# Критерии завершения реализации

## Базовый стандарт

Выбирай контроль по риску и заявляемому результату. Для изменения поведения нужны три слоя:

1. Автоматические проверки.
2. Тестовая проверка.
3. Профессиональное ревью.

## Базовый порядок

Используй существующие инструменты проекта; не устанавливай новый стек только ради checklist. Если проверки применимы, использовать такой порядок:

1. Formatter.
2. Linter.
3. Type checks.
4. Релевантные тесты.
5. Профессиональное ревью.

## Уровни строгости

### Низкий риск

Примеры:
- правка текста;
- безопасный rename;
- локальный комментарий без изменения поведения.

Минимум:
- базовая самопроверка;
- проверка измененного текста/формата и ссылок; formatter/linter только если они проверяют затронутый формат.

### Средний риск

Примеры:
- обычная feature;
- bugfix;
- локальный refactor;
- изменение тестового слоя.

Минимум:
- formatter/linter;
- type checks при наличии;
- релевантные тесты;
- ревью.

### Высокий риск

Примеры:
- DB change;
- API change;
- общая инфраструктура;
- авторизация;
- кросс-модульный refactor.

Минимум:
- formatter/linter;
- type checks;
- релевантные и расширенные тесты;
- ревью с акцентом на регрессии, риски и полноту покрытия.

## Что проверяет ревью

Достаточен self-review; отдельное формальное ревью нужно по запросу или для высокого риска. Уже полученные результаты сохраняют силу, пока относящиеся к ним код, зависимости, окружение и claim не изменились. Обязательные repo gates не отменяются; не дублируй их в каждом подключенном skill.

Профессиональное ревью должно отвечать как минимум на вопросы:

1. Нет ли логических ошибок?
2. Нет ли вероятных регрессий?
3. Достаточно ли тестов?
4. Не появилась ли лишняя сложность?
5. Соответствует ли изменение локальным стандартам?
