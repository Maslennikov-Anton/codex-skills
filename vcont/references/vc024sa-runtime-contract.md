# VC024SA Runtime Contract For VCont

For the full bidirectional Studio(front)/VCont(back) lifecycle and routing rules shared with the VCStudio skill, see `studio-vcont-contract.md`.

This reference keeps only VCont-runtime-facing facts from VC024SA.B. The full VCStudio developer guide belongs to the `vcstudio` skill. Use this file when a VCont task needs context from VCStudio-generated projects, bootfiles, communication blocks, or online commands.

## Boundary

- VCont owns runtime behavior: `vcontcfg.json`, IDE TCP XML commands, bootfile execution, FB runtime behavior, Modbus/OPC UA runtime semantics, HSB, logs, licensing, tests.
- VCStudio owns user workflows: project/workspace, `.vcsys`, GUI areas, preferences, ST editor, UserLibrary operations, monitoring UI, forcing UI, project backup/history, and communication setup screens.
- If a question asks how to click/configure something in Studio, use `vcstudio` skill.
- If a question asks what VCont receives, executes, logs, exposes over Modbus/OPC UA, or how to test runtime behavior, stay in `vcont` skill.

## Connection And Auth Boundary

- Studio resource IP/port and VCont `IpPort` must describe the same TCP endpoint.
- `UseAuth` in `vcontcfg.json` controls whether runtime checks authorization before executing commands.
- When auth is enabled, Studio/IDE session should initialize role through `AUTH` with token data; invalid token blocks further command execution.
- Treat connection, auth, and TLS settings as backend API boundary, not just GUI preferences.

## Runtime Connection

- VCStudio initiates communication with VCont.
- Commands are sent to the VCont address/port configured by `IpPort` in `vcontcfg.json` or by resource IP/port in Studio.
- VC024SA.B uses `61499` as the default VCont port for local resource access.
- Responses can be simple success/failure replies or structured replies with requested information, such as `READ` values or object lists.

## Bootfile Contract

- `vcont.fboot` is a text scenario of IDE XML commands placed next to the VCont executable for startup loading.
- VCStudio creates `vcont.fboot` as the same command set visible in `Консоль загрузки` during load.
- Runtime reads the bootfile at startup and creates the described database/application objects.
- Successful generated bootfile should contain `CREATE` commands for tasks/FBs/connections and final `START` commands for all relevant tasks.
- To make runtime read a newly generated bootfile: reboot resource, reset resource, or restart controller/runtime.
- `Сброс ресурса` semantics from Studio: clears load database, deletes bootfile, restarts with initial values.
- `Перезагрузка ресурса` semantics: service restarts Runtime. VC024SA success phrase: `Reboot successfully Executed`.
- `Создать и загрузить файл загрузки` sends the bootfile to controller. VC024SA success phrases: `The Load File command was sent successfully` and `Check BootSuccess`.

## Program Semantics From Studio To Runtime

- Project hierarchy generated by Studio maps to runtime names such as `APPLICATION.LOOP.FB` plus task resources.
- Every control loop must be assigned to a task; an empty task executes nothing.
- Periodic tasks execute FBs once per configured period.
- Event tasks execute by event input chains.
- Same-period restriction is a Studio/project rule from VC024SA: do not assign the same period to different tasks.
- If a cyclic task period is deleted in Studio, the task becomes event-based.
- FB creation order matters: implicit execution order is initially based on block addition/creation order.
- Explicit order can be represented by order properties or bootfile commands such as `ASSIGN Before`.
- Do not sort `CREATE FB` commands in a bootfile unless intentionally changing behavior.
- Event-loop runtime guardrails from VC024SA:
  - `E_RESTART`, commonly renamed `START`, generates one event on `COLD` after controller startup.
  - `E_CYCLE` can generate cyclic events when triggered by `START`; example `DT` is `1000 ms`.
  - Event inputs should be chained sequentially for deterministic processing.
  - Event branching makes order undefined.
  - Event closure/cycle can run without pauses and drive resource load to 100%.

## Values, Cold Start, Warm Start

- Full load writes initial values to controller database; subsequent connection/start is a cold start.
- `Онлайн загрузить КУ` loads a new/changed control loop without resetting current values to initial values.
- `Инициализация переменных` clears warm-start data and restarts resource with initial values.
- `Сохранение переменных` saves parameters for warm start.
- Initial values are undefined by default in Studio. After runtime start, full load, variable initialization, or resource reset, unconnected/uninitialized inputs usually become `false` for Boolean and `0` for analog/numeric.
- Online value writes and forcing affect the real runtime algorithm; treat them as control actions, not passive inspection.

## Modbus Runtime Contract From VC024SA

- Studio can generate runtime programs using blocks from `Communication\Modbus`; runtime receives FB instances, connections, aliases, and Modbus server/client configuration.
- VCont runtime can expose Modbus TCP server memory through `MBSERVER` and aliases.
- Runtime device/server `Options` use space-separated key-value pairs: `name1=value1 name2=value2`. Parameters with suitable defaults may be omitted; see `runtime-options.md` for `MBCLIENTTCP`, `MBCLIENTRTU`, `MBCLIENTRTUOVERTCP`, `MBSERIALPORT`, `MBSERVER`, `EIPDEV`, `KNXDEV`, and `PRBDEV`.
- `MBCLIENTTCP.HsbAlg` is important for HSB: default `1` makes `MAIN`, `STANDALONE`, and `RESERVE` connect at startup; value `2` makes only `MAIN` and `STANDALONE` connect at startup.
- Multiple Modbus TCP servers have independent memory: `MBSRV1.QX1` is not `MBSRV2.QX1`.
- Publish FB port values into runtime Modbus memory using `ServerName.Register`, for example `MBSRV1.QX1`.
- Prefer `QX` or `IX` for BOOL values because they are 1-bit areas.

Server memory map from VC024SA:

| Register | Modbus address | Size | Access | Functions | Types |
|---|---:|---:|---|---|---|
| `QX0-QX65535` | `0-65535` | 1 bit | RW | `01`, `05`, `15` | `BOOL` |
| `IX0-IX65535` | `0-65535` | 1 bit | RO | `02` | `BOOL` |
| `IW0-IW65535` | `0-65535` | 16 bit | RO | `04` | `INT`, `WORD` |
| `MW0-MW29999` | `0-29999` | 16 bit | RW | `03`, `06`, `16` | `INT`, `WORD` |
| `MD0-MD9999` | `30000-49998` | 32 bit | RW | `03`, `06`, `16` | `DINT`, `REAL` |
| `ML0-ML3750` | `50000-65000` | 64 bit | RW | `03`, `06`, `16` | `LINT`, `LREAL` |

`MBWRITE_PACK` runtime-facing facts:

- Purpose: write data to remote Modbus TCP/RTU device.
- Ports from VC024SA: `REQ`, `CNF`, `DEVICE`, `ENABLE`, `ADDRESS`, `FORMAT`, `WD01...`, `STATUS`.
- `ADDRESS` format: `start_address:function`.
- Write functions: `05`, `06`, `15`, `16`.

`MBREAD_PACK` runtime-facing facts:

- Purpose: read data from remote Modbus TCP/RTU device.
- Ports from VC024SA: `REQ`, `CNF`, `DEVICE`, `ENABLE`, `ADDRESS`, `FORMAT`, `WD01...`, `STATUS`.
- Read functions: `01`, `02`, `03`, `04`.
- Caveat: VC024SA table reuses write wording and `WD01`; verify actual typelibrary/runtime interface before coding assertions.

Common `_PACK` formats:

- `C`: bool, 1 bit.
- `F4`: real, 32 bit.
- `F8`: lreal, 64 bit.
- `S2`: int 16 bit; also listed for uint 16 bit in the document.
- `S4`: dint, 32 bit.

Common `_PACK` status codes:

- `0`: no connection or wrong block fields.
- `1`: no errors.
- `101`: illegal function.
- `102`: illegal data address.
- `103`: illegal data value or invalid `FORMAT`.
- `104`: slave device failure.
- `105`: acknowledge.
- `106`: slave busy.
- `107`: negative acknowledge.
- `108`: parity error.
- `110`: gateway path unavailable.
- `111`: gateway target device failed to respond.
- `112`: bad CRC.
- `113`: bad data.
- `114`: illegal exception code.
- `116`: too much data.
- `117`: response from wrong slave.
- `200+`: user error codes.

Diagnostic blocks and counters to recognize:

- `MBSERIALDIAG`: `PORT`, `RST_CNT`, `CONNECTED`, `BAUD`, `PARITY`, `TIMOUT`, `DELAY`, `MSGS_TX`, `MSGS_RX`, `MSGS_TO`, `MSGS_TA`, `T_ERR`, `QUEUE`, `DUPLICATES`, `EMBBADCRC`, `EMBBADDATA`, `EMBBADEXC`, `EMBUNKEXC`, `EMBMDATA`, `EMBBADSLAVE`.
- `MBDEVICERTU`: `DEVICE`, `RST_CNT`, `CONNECTED`, `PORT`, `SLAVEID`, `MSGS_TX`, `MSGS_RX`, `MSGS_TO`, `MSGS_TA`, `T_ERR`, `EMBBADCRC`, `EMBBADEXC`, `EMBBADDATA`, `EMBUNKEXC`, `EMBMDATA`, `EMBBADSLAVE`.
- `MBDEVICETCP`: `DEVICE`, `RST_CNT`, `ADDRESS`, `PORT`, `WINDOW`, `TIMOUT`, `CONNECTED`, `MSGS_TX`, `MSGS_RX`, `MSGS_TO`, `PENDING`, `QUEUE`, `DUPLICATES`.
- Keep documented `TIMOUT` spelling when answering about documented ports; do not silently normalize to `TIMEOUT`.

## OPC UA Runtime Contract From VC024SA

- Runtime may create an internal OPC UA server automatically at startup; it is available to external clients.
- Blocks described by VC024SA: `CLIENT`, `SUBSCRIBE`, `PUBLISH`.
- Configure `CLIENT` with either only inputs or only outputs.
- `SUBSCRIBE` has no data inputs; it reads values when server values update.
- `PUBLISH` creates/writes tags on local internal server only and has value inputs.

Common ID grammar:

```text
opc_ua[ACTION;opc.tcp://IP:Port#;Path,Namespace:IdentifierType=Identifier]
```

- Actions: `READ`, `WRITE`, `SUBSCRIBE`.
- Local server may omit IP and port.
- Default OPC UA port: `4840`.
- Namespace defaults to `0`; if omitted, the colon is omitted too.
- Identifier types: `i` numeric, `s` string, `b` byte string, `g` GUID.
- Example remote write ID: `opc_ua[WRITE;opc.tcp://IP-сервера:4840#;/Objects/TAGS/TAG1,0:s=TAG1;/Objects/TAGS/TAG2,0:s=TAG2]`.
- Example local publish ID: `opc_ua[WRITE;/objects/QT01,0:s=QT01;/objects/QT02,0:i=123456]`.

## VC024SA Caveats Relevant To Runtime Work

- OPC UA is numbered again as `8.1`, conflicting with `8.1 Modbus`.
- Some Modbus TCP Server text says “настроить клиента” and mentions `Modbus TCP Client` although the section is about server.
- Table 6 says server name is used only in CODESYS; treat as suspicious wording in VCStudio context.
- `Modbus Serial Portrs` appears with a typo.
- `MBDEVIERTU` appears instead of `MBDEVICERTU` in several places.
- `MBREAD_PACK` table reuses write wording and `WD01`.
- `FORMAT` lists `S2` for both int and uint.
- OPC UA text has typos in `индификатора/Индификатор` and inconsistent spacing in `opc_ua [WRITE;`.
- Section 8 mentions `ETHERNET IP`, but the extracted VC024SA text does not expand it.
