# Licensing, Trial And Demo Builds

Этот reference фиксирует актуальную модель лицензирования VCont. Основные источники: локальные документы из `/home/ant/IdeaProjects/vcont-hsb/source` от 2026-05-15 (`vcontwork.txt`, `litsenzirovanie_sredy_ispolnenija_doc-000248.pdf`, `litsenzirovanie_virtual_nyh_mashin_doc-000240.pdf`, `litsenzirovanie_fizicheskih_mashin_doc-000244.pdf`, `proverka_litsenzij_doc-000242.pdf`) и Allure TestOps project `VCont` (`projectId=3`) как источник тест-кейсов.

## Runtime Environment

Docker/runtime baseline для VCont - Ubuntu 24.04. Это общее правило для VCont, не связанное с типом лицензии.

## Виды поставок

- Обычный VCont для внутренней команды разработки: без runtime-ограничений.
- Лицензированный VCont для продажи: commercial/runtime license, ограничения задаются лицензионным сертификатом.
- Trial Lite: в имени `.deb` ожидается `tria-lite`/`trial-lite`; работает 30 минут, поддерживает OPC UA, не загружает `vcont.fboot`.
- Demo / Trial Full: в имени `.deb` ожидается `tria-full`/`trial-full`; работает 24 часа, поддерживает OPC UA, ограничен 15 точками ввода-вывода, срок действия до 1 января следующего года.
- No-license режим licensed build без установленной лицензии: ограниченный режим без лицензионного сертификата.

Важно: не называй любую сборку с `trial` в имени одинаково. `trial-lite` и `trial-full` имеют разное поведение. Проверенный пакет `vcont-develop-trial-1.1.0.22153...trial-full.deb` относится к Demo / Trial Full модели, поэтому его 24-часовой лимит и успешная загрузка `vcont.fboot` не противоречат Trial Lite ограничениям.

## Общие принципы лицензирования

Система исполнения лицензируется по основным параметрам:

- поддерживаемые драйверы и протоколы;
- максимальное количество сигналов/переменных ввода-вывода (`VARS`, AI/AO/DI/DO/Digital);
- функция резервного копирования/HSB;
- дополнительные возможности драйверов.

Лицензируемые функции в документах:

- `VARS`: учитываются переменные, полученные с поля и обрабатываемые внутри контроллера. Переменные, которые только шлюзуются в MB Server или OPC UA server без обработки внутри контроллера, не учитываются.
- Базовые драйверы OPC UA, Modbus TCP и MQTT включены по умолчанию.
- Лицензируются advanced-возможности: `Modbus ADVANCED` (асинхронный режим, более одного Modbus TCP server), `OPC UA ADVANCED` (полноценный OPC UA server с HDA/Pub/Sub/discovery), Ethernet/IP, Bacnet и будущие драйверы.

Без лицензионного сертификата возможности среды исполнения должны быть ограничены:

- не более 30 точек ввода-вывода;
- не более 30 минут непрерывной работы.

## Лицензионный сертификат

Лицензионный сертификат содержит информацию, необходимую для запуска конкретного экземпляра VCont:

- заказчик: наименование и ID;
- партнер/дистрибьютор/системный интегратор: наименование и ID;
- `ControllerId`;
- версия сборки контроллера;
- тип лицензии;
- дата активации;
- дата окончания лицензии;
- доступный функционал и лимиты, например `Vars`, `CopiesMBServer`, `modbus_tcp`, `opc_ua`.

Пример полей из документов:

```json
{
  "OrganizationName": "NoName",
  "OrganizationId": 1234567,
  "ControllerId": "21.2025.764798",
  "File": "data.bin",
  "VersionBuild": "1.1.0.0",
  "TypeLicense": "demo",
  "Date": "12.06.2025",
  "UpdateTo": "12.08.2025",
  "Vars": 100,
  "CopiesMBServer": 1,
  "Hash": "..."
}
```

После окончания срока действия лицензии функционал контроллера не изменяется для уже выпущенной версии: просроченная лицензия не должна работать с более новой версией среды исполнения, только с версией, для которой она была выпущена, или более ранними.

## Формирование лицензии

Документы описывают следующую общую цепочку выпуска лицензии:

1. Клиент или Isource получает идентификаторы целевой машины:
   - для виртуальной машины - PCR/TPM-метрики, UUID системы и параметры организации;
   - для физической машины - аппаратные UUID разных устройств через CreatorLicense.
2. Клиент передает в Isource файл с идентификаторами и параметры лицензии.
3. Isource генерирует `ControllerId`.
4. Isource патчит VCont значением `ControllerId`.
5. Isource вычисляет хэш VCont.
6. Isource формирует `license.json` с данными организации, controller ID, версией сборки, типом лицензии, сроками и лимитами.
7. Isource подписывает `license.json`, получая `data.sig`.
8. Isource объединяет `license.json` и `data.sig` в `license.bin`.
9. Isource формирует `data.bin` с аппаратной привязкой.
10. Клиент получает `license.bin`, пропатченный VCont, `data.bin` и публичный ключ.

Для активации через VCStudio контроллер должен:

- сверить `ControllerId` из сертификата с ID контроллера;
- проверить цифровую подпись сертификата публичным ключом;
- применить настройки лицензии;
- сохранить лицензию на контроллере без возможности удаления, в режиме только чтение;
- при активации новой лицензии сохранить старую в архив `/var/OldVContLic/`.

## Проверка лицензии

Основная модель:

- `license.bin` состоит из `license.json` и `data.sig`;
- подпись `license.json` проверяется публичным ключом;
- `ControllerId` из лицензии сверяется с ID в VCont;
- для x86-64 дополнительно проверяется UUID системы и `data.bin`, включая проверку PCR-регистров TPM;
- один раз в час проверяется хэш VCont из лицензии с runtime-хэшем бинарника, чтобы обнаружить изменение бинарного файла.

В случае успешности всех проверок контроллер продолжает работу. Если расходится `ControllerId`, подпись, UUID/TPM-привязка или хэш бинарника, VCont должен остановиться или отказать в активации с соответствующим кодом ошибки.

Для виртуальных машин:

- клиент собирает PCR/TPM-метрики и параметры организации/типа лицензии;
- Isource генерирует `license.bin`, `data.bin`, патчит VCont значением controller ID и передает публичный ключ;
- клиент кладет `license.bin`, пропатченный VCont, `data.bin` и публичный ключ в директорию виртуального контроллера.

Детальный workflow для виртуальных машин:

- клиент запускает скрипт/программу, снимающую PCR TPM и сохраняющую результат в `PCR_FILE`;
- в интерактивном интерфейсе указываются `OrganizationName`, `OrganizationId`, `TypeLicense`;
- формируется `organization.json`;
- `PCR_FILE` и `organization.json` архивируются в `.bin`;
- Isource на основе архива и параметров лицензии генерирует `license.bin`;
- Isource патчит VCont, генерирует `data.bin` и публичный ключ;
- `data.bin` содержит зашифрованное значение UUID с использованием TPM и политики PCR-регистров.

Для физических машин:

- CreatorLicense снимает аппаратные UUID целевой машины;
- клиент передает файл UUID в Isource;
- Isource формирует пропатченный VCont и лицензию;
- после загрузки в VCStudio должно отображаться сообщение с типом лицензии, количеством точек ввода-вывода и датой действия лицензии.

Детальный workflow для физических машин:

- CreatorLicense должен опрашивать физические устройства ПК/ноутбука и получать аппаратные UUID материнской платы, процессора и других устройств;
- CreatorLicense генерирует список UUID в файл;
- клиент может выбрать подготовленное Isource устройство или свое физическое устройство;
- если устройство клиента, Isource передает клиенту программу для генерации файла UUID;
- клиент запускает программу на целевой машине и передает файл UUID в Isource;
- Isource формирует пропатченный VCont и лицензию;
- если нужно расширить лимиты, клиент повторно передает UUID, тип лицензии и желаемое количество точек I/O;
- если UUID изменился, клиент должен заново сгенерировать UUID-файл и получить новую лицензию.

## Подпись И Защита От Копирования

Документы фиксируют два базовых способа подписи и отдельную схему защиты от копирования.

OpenSSL dgst:

```bash
openssl genrsa -out privatekey.pem 4096
openssl dgst -sign privatekey.pem -out hello.sig hello
openssl rsa -in privatekey.pem -outform PEM -pubout -out publickey.pem
openssl dgst -verify publickey.pem -signature hello.sig hello
```

Успешная проверка возвращает `Verified OK`, неуспешная - `Verification Failure`. Проблема простой подписи бинарника: одна подпись подходит для любого количества идентичных бинарников, поэтому она не защищает от копирования.

GNU Privacy Guard:

```bash
gpg --full-generate-key
gpg --export-secret-keys > privatekey
gpg --output hello.sig --detach-sign hello
gpg --export > publickey
gpg --verify hello.sig hello
```

У GPG остается та же проблема: подпись подтверждает подлинность, но не привязывает бинарник к конкретной машине.

Схема защиты от копирования:

- на стороне сервера соединить уникальный идентификатор машины и бинарник;
- вычислить хэш объединенных данных;
- подписать хэш закрытым ключом;
- передать клиенту бинарник, подпись и публичный ключ;
- на стороне клиента при старте считать серийный номер/CPU ID;
- вычислить хэш из бинарника и локального серийного номера;
- проверить подпись публичным ключом.

Пример из документов:

```bash
cat executable serial_num.txt > combined
sha256sum combined > hash
rm combined
openssl dgst -sign privatekey.pem -out signature.sig hash
openssl rsa -in privatekey.pem -outform PEM -pubout -out publickey.pem
openssl dgst -verify publickey.pem -signature signature.sig hash
```

Такая подпись будет валидна только при совпадении и бинарника, и машинного идентификатора. Отмеченная уязвимость: подмена утилиты получения `cpuid` на программу, которая возвращает нужный идентификатор.

## Licensed / Commercial Build

Licensed runtime должен запускаться с корректной лицензией и поддерживать `vcont.fboot`, если это не ограничено конкретной лицензией или конфигурацией.

Ожидания из TestOps:

- Test case `1435`: `03. Проверка работы лицензионной версии vcont x86_64`.
- Test case `1437`: `04. Проверка работы лицензионной версии vcont aarch64(arm)`.
- В логах ожидается подтверждение вида `Verification was completed successfully. License type - runtime`.

Если licensed build не грузит bootfile при корректной лицензии и конфигурации, это дефект или проблема окружения/лицензии, а не trial-ограничение.

## Trial Lite

Trial Lite - короткая триальная сборка:

- в имени `.deb` ожидается `tria-lite`/`trial-lite`;
- работает 30 минут;
- поддерживает OPC UA;
- не загружает `vcont.fboot`;
- при запуске как service с restart-политикой ожидается перезапуск после завершения лимита.

Соответствие TestOps:

- `1381`: 30-минутный лимит trial;
- `1382`: service restart после 30 минут;
- `1379`: переподключение VCStudio не продлевает trial;
- `1383`: отсутствие автозагрузки `fboot` в trial;
- `1380`: очистка программы после restart, статус Draft.

Trial Lite smoke не должен ожидать успешную автозагрузку `vcont.fboot`. Для этой модели ожидаемо диагностировать запрет bootfile autoload и завершение после 30 минут.

## Demo / Trial Full

Demo / Trial Full - расширенная демо-сборка:

- в имени `.deb` ожидается `tria-full`/`trial-full`;
- работает 24 часа;
- поддерживает OPC UA;
- ограничена 15 точками ввода-вывода;
- срок действия до 1 января следующего года;
- `vcont.fboot` может загружаться и исполняться.

Локальная проверка пакета `vcont-develop-trial-1.1.0.22153.lin.x86_64.opcua.trial-full.deb` подтвердила:

- лог содержит `TRIAL version, work time is limited to 24 hours`;
- `vcont.fboot` autoload не блокируется;
- лог содержит `Boot file correctly loaded`;
- программа из `vcont.fboot` реально исполняется, что подтверждается ростом счетчика через IDE `READ`;
- live-команды VCStudio/IDE для создания ФБ, связей, assignment и `START` выполняются.

Не применяй TestOps oracle `trial-lite` к `trial-full`/demo пакету. Если пакет `trial-full` грузит bootfile и работает 24 часа, это соответствует demo-модели из `source/vcontwork.txt`.

## Практические правила для тестов

- Сначала классифицируй пакет по имени и логам: internal, licensed, `trial-lite`, `trial-full`/demo, no-license.
- Для `trial-lite` проверяй 30 минут, запрет `vcont.fboot`, OPC UA и restart/service behavior.
- Для `trial-full`/demo проверяй 24 часа, лимит 15 I/O, OPC UA, загрузку и исполнение `vcont.fboot`.
- Для licensed проверяй `license.bin`, `data.bin`, публичный ключ, `ControllerId`, тип лицензии и лимиты `Vars`/`CopiesMBServer`.
- Для short smoke недостаточно проверить только старт процесса: подтверждай IDE `QUERY`, при наличии программы - `READ` рабочих пинов, и релевантные строки `vcont.log`.
