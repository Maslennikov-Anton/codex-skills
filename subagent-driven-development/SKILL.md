# Subagent-Driven Development

Используй этот skill, когда пользователь явно попросил subagents, parallel agents, delegation, agent workflow или когда локальный standing opt-in разрешает subagent workflow для текущей задачи. Цель: ускорить независимые части работы без потери контроля, качества и проверяемости.

## Standing Opt-In

В локальном стандарте пользователя действует standing opt-in на неявный запуск subagents для инженерных задач, если:

- задача реально выигрывает от параллельной или делегированной работы;
- можно выделить независимые subtasks;
- у каждого subagent есть четкий ownership;
- основной агент не блокируется на делегированном immediate next step;
- результат можно проверить локально перед финальным ответом.

Если текущая системная среда требует явного разрешения на subagents, используй это правило только после такого разрешения в диалоге или явной пользовательской настройки.

## Workflow

1. Быстро выдели critical path:
   - что должен делать основной агент прямо сейчас;
   - какие sidecar tasks можно делегировать без блокировки;
   - какие tasks нельзя делегировать, потому что они требуют тесной координации или немедленного результата.
2. Сформулируй bounded subtasks:
   - цель;
   - входной контекст;
   - expected output;
   - write ownership по файлам или зонам;
   - запрет откатывать чужие изменения;
   - команды проверки, если они известны.
3. Запусти только реально полезных subagents:
   - `explorer` для узких вопросов по codebase;
   - `worker` для disjoint code changes;
   - не запускай несколько агентов на один и тот же unresolved вопрос.
4. Пока subagents работают, выполняй non-overlapping работу основным агентом.
5. После завершения каждого subagent:
   - прочитай результат;
   - проверь changed files или evidence;
   - интегрируй только то, что проходит review;
   - закрой thread, если он больше не нужен.
6. Перед финальным ответом:
   - проверь общий diff;
   - запусти релевантную verification;
   - явно сообщи, что проверено и что не удалось проверить.

## Review Gates

Для code-changing subagents используй два уровня review:

1. Spec compliance:
   - задача выполнена именно в заявленном scope;
   - нет лишней функциональности;
   - соблюден ownership;
   - нет пропущенных acceptance criteria.
2. Code quality:
   - решение следует local patterns;
   - нет очевидных regressions;
   - тесты и проверки соответствуют риску;
   - нет конфликтов с параллельными изменениями.

Если review выявил проблему, не исправляй вслепую поверх результата. Сначала реши, лучше ли вернуть задачу тому же subagent, исправить локально или пересобрать ownership.

## Что делегировать

- Независимый поиск по codebase.
- Bounded реализацию в отдельных файлах или модулях.
- Параллельную проверку гипотез.
- Подготовку тестов для отдельного слоя.
- Review уже готового diff.

## Что не делегировать

- Immediate blocking step, без которого основной агент не может двигаться.
- Глубоко связанную архитектурную развилку без решения владельца.
- Изменения в live/external systems без явного разрешения.
- Разрушительные git/file операции.
- Tasks с пересекающимся write ownership.

## Prompt Contract

Каждый worker prompt должен содержать:

- что сделать;
- какие файлы или зоны принадлежат worker'у;
- что не трогать;
- что другие агенты могут менять параллельно;
- какие проверки запустить;
- что вернуть в финальном отчете: summary, changed paths, tests, risks.

Используй шаблоны из [references/prompt-contracts.md](references/prompt-contracts.md), когда задача достаточно сложная.

## Формат ответа

Когда используешь subagents, возвращай:

1. Какие subtasks делегированы и почему.
2. Какие файлы или зоны были закреплены за каждым subagent.
3. Что сделал основной агент параллельно.
4. Какие результаты subagents приняты, изменены или отклонены.
5. Какая verification выполнена после интеграции.
