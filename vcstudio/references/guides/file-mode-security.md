## Включение и отключение безопасности — VCONT-2027

Настройка относится только к **file mode**, конкретному проекту `.vcsys`. Поведение database mode этой задачей не меняется.

| Состояние | Открытие существующего проекта | Блокировка |
| --- | --- | --- |
| Безопасность включена | Обычный вход локальным пользователем проекта | Работает |
| Безопасность штатно отключена и сохранена | Без login dialog, автоматически как admin | Не запускается |
| Секции настройки нет | Считать безопасность включённой | Обычная логика |
| Подпись отсутствует/неверна у попытки отключить защиту | Отключение не принимается; требуется обычная авторизация | Защита не обходится |

Путь UI: редактор **проекта**, вкладка `Безопасность`, флажок `Включить безопасность`. Изменение доступно только admin. Значение `ExtendedSettings/SecuritySettings/@fileModeAuthDisabled` имеет обратный смысл: **снятый** флажок соответствует `true`. С настройкой связаны `fileModeAuthVersion` и `fileModeAuthSignature`; ручная подстановка `true` не является корректным отключением. Менять и сохранять настройку нужно через Studio.

Повторное включение требует подтверждения `Включить безопасность` → `Продолжить`; нужно знать пароль активного обычного администратора. Пользователи при штатном выключении/включении не должны теряться.

Отдельная ветвь VCONT-2127, пункт 12: при **валидном штатном auth disable**, но повреждённом users-контейнере, сохраняется автоматический вход admin; при последующем включении security ожидается стандартный контейнер. Не смешивай повреждение users blob с повреждением подписи настройки отключения: это разные проверки.

## Создание, открытие и роли — VCONT-2127

**Новый файловый проект** после `Создать` сразу открывается под стандартным admin. Дополнительный login dialog после создания не требуется. При **следующем открытии существующего защищённого файла** окно входа требуется. Эти два пути нельзя объединять одним ожиданием «всегда показать Вход».

| Пользователь нового проекта | Роль | Состояние |
| --- | --- | --- |
| `admin`, пароль `admin` | admin | Активен |
| `engineer` | engineer | Неактивен; для обычного входа admin должен активировать его и задать пароль |
| `recovery` | Системный admin | Активен; не обычный администратор для правил сохранения доступа |

`admin/admin` — начальные данные нового/сброшенного контейнера, не общий пароль всех файлов. Контейнер принадлежит проекту. Логины регистронезависимы: `admin`, `Admin`, `ADMIN` — один пользователь. Пустые/пробельные и повторные логины запрещены. Неверный пароль, неизвестный или неактивный пользователь должны получать отказ без падения Studio; ошибочный ввод не меняет существующих пользователей.

Engineer может редактировать проект, но не управляет пользователями и security-настройками. При deployment должна передаваться его фактическая роль engineer. Успешный вход admin не покрывает этот контракт.

Admin управляет созданием, редактированием, активацией, блокировкой/разблокировкой, удалением и паролями. Кнопки и контекстное меню проверяются отдельно. Recovery нельзя удалить, деактивировать, блокировать, переименовать, изменить ему роль или назначить постоянный пароль.

Последнего **обычного активного** admin нельзя удалить, заблокировать/деактивировать или понизить до engineer. Recovery при подсчёте не учитывается. Для проверки разрешённых операций сначала создай другого активного admin. Отдельно действует запрет удаления **текущего** пользователя в UI: наличие admin2 не означает разрешения удалить вошедшую учётную запись. Для удаления исходного admin войди под admin2. Это разграничивает пункт 6 задачи и уточнение PDF.

Вкладка `Безопасность` видна после входа с ролью `admin`. Она управляет локальными пользователями именно этого `.vcsys`, а не общим списком всех проектов.

По инструкции контейнер пользователей внутри `.vcsys` зашифрован и связан с проектом; пароли хранятся как стойкие хеши. Это не описание алгоритмов и не результат криптографического аудита.

При создании локального пользователя admin задаёт логин, имя, пароль и роль.

## Пароли: существенное уточнение пункта 8

Смена собственного пароля требует правильного старого пароля и согласованного непустого нового/подтверждения. Ошибка и отмена не должны менять пароль. После перезапуска старый пароль отвергается, новый работает. Проверять отдельно admin и engineer.

**Не принимай исходный пункт 8 VCONT-2127 об обязательной смене временного пароля после admin reset за действующий безусловный oracle.** В комментарии от **17.08.2026 16:51** явно согласовано: «Пункт 8 не реализован в описанном виде, в данный момент мы не создаем временный пароль и не требуем его смену».

Это подтверждено для поставленной сборки: `FileModeUsersSupport.setPasswordByAdmin(...)` после смены пароля записывает `mustChangePassword=false`. В `LoginDialog` есть общий обработчик `handleMandatoryPasswordChange`, но наличие обработчика не означает, что admin reset выставляет флаг. Обещание PDF о предложении сменить пароль после сброса расходится с этим уточнением и реализацией. Отсутствие принудительной смены после такого сброса само по себе не является дефектом данной согласованной версии. Проверки обязательной смены для контейнера, в котором флаг действительно выставлен, — отдельный сценарий.

Устаревшее действие смены пароля в меню `Файл` удалено. В сборке зарегистрирована команда `org.eclipse.fordiac.ide.application.commands.changeOwnPassword`; смену своего пароля не подменяй сбросом пароля выбранного пользователя в таблице admin.

## Хранение, привязка и штатные операции

В `.vcsys` используются `fileModeUsersVersion`, `fileModeUsersBlob`, `fileModeUsersBindingTag`. В проверенной сборке они находятся в `ExtendedSettings/SecuritySettings`, как и настройки отключения авторизации. Это отличается от первоначального ожидания расположения в `Project`, отмеченного в пункте 9 задачи; не ищи их только на корне XML.

По контракту контейнер зашифрован и связан с проектом, пароли не хранятся открытым текстом. Проверяй конкретные заданные пароли, отсутствие открытого JSON с пользователями/passwordHash, непустые blob/binding и корректность XML. Само вхождение строки `admin` не доказывает утечку пароля: она может быть логином или иным текстом. Проверка XML не заменяет успешный вход с сохранёнными учётными данными.

Обычное сохранение и штатное переименование должны сохранять пользователей/пароли; binding пересчитывается Studio. **Save Project As** должен переносить всех пользователей, их роли/состояния/пароли; исходник продолжает работать, `audit` в копию не переносится. Для проверки предварительно измени пароль admin и создай admin2/engineer2: один вход `admin/admin` не отличает сохранение контейнера от его ошибочного сброса.

Backup/Restore должен возвращать пользователей и пароли снимка. Текущий локальный audit сохраняется, не заменяется из backup; появляется `PROJECT_RESTORED`. Это восстановление версии проекта, в отличие от security recovery, которое сбрасывает пользователей к стандартным.

В экспорте с VCONT-2127 связаны дефекты **VCONT-2221** «Копия получает только стандартный набор пользователей» и **VCONT-2222** «PROJECT_RESTORED отсутствует в аудите», оба со статусом `Новый` на момент выгрузки. Это историческое свидетельство найденных проблем, не доказательство их наличия/исправления в любой следующей сборке. Положительные тесты Save As/Restore сохраняют требуемые ожидания; их нельзя превращать в xfail или принимать стандартных пользователей вместо сохранённых.

## Аудит и блокировка

Файл аудита: `<каталог проекта>/audit/file-mode-security-audit.jsonl`. Каждая строка — JSON с `timestampUtc`, `projectName`, `eventType`, `actorLogin`, `result`, а при необходимости `targetLogin`. Ожидаемые события:

```text
LOGIN_SUCCESS  LOGIN_FAILED  RECOVERY_LOGIN_SUCCESS
USER_CREATED  USER_UPDATED  USER_DELETED
PASSWORD_CHANGED  USER_ACTIVATED  USER_DEACTIVATED
FILE_MODE_AUTH_DISABLED_ENABLED  FILE_MODE_AUTH_DISABLED_DISABLED
PROJECT_RESTORED
```

Не угадывай смысл двух обратных по названию событий переключения по одному suffix: проверяй действие вместе с сохранённым `fileModeAuthDisabled`. В журнале не должно быть паролей, passwordHash, recovery-пароля, полного Session ID и users blob. Login может менять security-поля и писать аудит; абсолютное ожидание «все файлы проекта неизменны после входа» нужно оценивать относительно конкретного read-only контракта, а не освобождать любые изменения от проверки.

При включённой защите ручная/idle-блокировка должна закрывать рабочую область и меню, отвергать неверный пароль, снимать блокировку правильным паролем текущего пользователя и сохранять роль. Проверяются admin/engineer и resize/move/minimize/restore окна. При auth disable блокировки нет. Один idle timeout `0` в настройках и отключённая безопасность проекта — разные причины отсутствия блокировки.

## Указания для тестов и диагностики

- Фиксируй file/DB mode и состояние безопасности входного проекта. Не отключай её во всех фикстурах ради прохождения login/lock-тестов.
- После **создания** проверяй фактический проект, путь, admin-сеанс и начальных пользователей; после **открытия защищённого существующего файла** сохраняй строгую проверку login dialog и введённого пользователя.
- API авторизации файлового режима должен получать целевой `Path`/login session. Старый вызов `LoginDialog.auth(user, password, shell)` до открытия файла передаёт null вместо пути и не эквивалентен штатному входу по `.vcsys`.
- В текущем file-mode UI используется `FileModeEditUsersWidget`: действия представлены SWT `Button`, не прежними `ToolItem`; кнопки загрузки пользователей в VCont в этом локальном виджете нет. Таблица в русской локализации по-прежнему имеет `Логин`, `ФИО`, `Группы`, `Статус`; подпись `Группы` не означает прежнюю серверную ролевую модель. В диалоге создания подписи полей без двоеточий, роли `Admin` / `Engineer`; точные подсказки кнопок и ограничения Combo-селекторов — в карте влияния на тесты. Исторический DB-контракт ТК 1048 этим файловым UI не заменяется.
- `Недавние проекты` в текущем `RecentProjectsContributionItem.fill` включается, когда список непуст и ни один проект не открыт. Требование «disabled при пустом списке» не равнозначно «пункт отсутствует» и не отменяет дополнительного условия текущей сборки.
- Контракты отрицательных входов, engineer, последнего admin, auth disable, восстановления, аудита и подписей требуют отдельных положительных/отрицательных сценариев. Видимая вкладка `Безопасность` и зелёный smoke входа admin их не покрывают.
