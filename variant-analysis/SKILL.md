# Поиск вариантов известного дефекта

Используй, когда известен конкретный дефект и нужно проверить, где еще встречается его причина. Статус в локальном наборе — `experimental`. Совпадение текста дает кандидата, а не подтвержденный баг.

## Workflow

1. **Определи исходный дефект.** Запиши нарушенный контракт, известное место, предусловия, вход/действие и наблюдаемый результат. Если причина еще не установлена, сначала используй `systematic-debugging`.
2. **Откалибруй поиск.** Подбери точный запрос, который находит известное место в текущем коде. Если исправление уже применено, проверь запрос на доступной старой ревизии или reproducer и отдельно ищи по текущей; не откатывай рабочее дерево ради поиска.
3. **Расширяй по одному признаку.** Имя, конкретная операция, тип данных, соседний путь исполнения. Читай новые совпадения после каждого расширения. Смотри за пределами исходного модуля в пределах согласованного репозитория; уважай исключения поиска.
4. **Проверь кандидатов.** Для каждого проследи условия вызова, данные и возможную защиту. Воспроизведи нарушение локально, когда это осуществимо и входит в задачу. Отличай подтвержденный дефект, подозрение и false positive.
5. **Заверши ограниченный sweep.** Остановись при исчерпании выбранных направлений или бюджета. Если шум преобладает, уточни запрос/возьми другую ось вместо бесконечного расширения. Назови непроверенные области; отсутствие совпадений не доказывает отсутствие вариантов.

Для запросов, triage и формы результата читай [references/search-and-triage.md](references/search-and-triage.md).

## Инструменты и границы

- Начинай с `rg` и чтения callers/tests. Для контекстных конструкций может быть полезен AST; для data flow — уже доступные Semgrep/CodeQL. Не устанавливай тяжелый анализатор и не строй database, когда узкого поиска достаточно.
- Выполняй поиск последовательно. Parallel agents допустимы только при отдельной авторизации; этот skill ее не добавляет.
- Анализ не разрешает исправления, запуск на живой системе или публикацию отчета во внешний сервис. Продолжай в пределах пользовательской задачи.
- Для общего ревью без известной причины используй `code-review-professional`; для новых defect families — `fuzzing-bug-hunter`.
- Если исправления входят в задачу, применяй их к подтвержденным вариантам и проверяй regression oracle. Не меняй все текстовые совпадения автоматически.
- Новое CI-правило предлагай, когда оно достаточно точное и полезно повторно; разовый поиск не требует обязательного CI gate.

Результат: исходный контракт/root cause, область и команды поиска, таблица кандидатов с evidence и статусом, непроверенные области и следующий полезный шаг.
