# Property-Based Testing

Используй, когда контракт задает проверяемое свойство для семейства входов, а перебор примеров оставляет существенные пробелы. Статус подхода в локальном наборе — `experimental`: пробуй на подходящих небольших задачах, не заменяй им обычные тесты повсеместно.

## Выбор свойства

Сначала зафиксируй контракт и допустимый домен. Свойство должно следовать из спецификации, документированного поведения или независимой эталонной модели.

| Свойство | Пример проверки | Ограничение |
|---|---|---|
| Roundtrip | `decode(encode(x)) == x` | Только на поддержанном домене; учитывай нормализацию и потери |
| Идемпотентность | `normalize(normalize(x)) == normalize(x)` | Только если повторная нормализация обещана контрактом |
| Сохранение | Разбиение содержит каждый исходный ID ровно один раз | Сравнивай мультимножества, чтобы не потерять дубликаты |
| Независимый oracle | Новая реализация согласуется с эталонной | Не переписывай ту же формулу в assertion |
| Метаморфное отношение | Перестановка входа сохраняет обещанный результат | Порядок может быть частью контракта |

Если полезного свойства нет, используй конкретные example-based tests. Проверка «не упало» полезна лишь при явно заданном контракте обработки входа, а не как замена смысловым assertions.

## Выполнение

1. Найди существующую библиотеку и принятый способ запуска. Для Python смотри [references/hypothesis.md](references/hypothesis.md); версии и незнакомые API сверяй с установленной библиотекой и ее документацией.
2. Генерируй допустимые входы напрямую. Зависимые поля строй согласованно; не отбрасывай почти все примеры через `assume()` или фильтры.
3. Добавь важные известные границы отдельными примерами. Пустое значение, повторы, Unicode и экстремальные числа включай только когда они входят в домен.
4. Ограничь бюджет по цене целевого кода. Изолируй состояние между примерами; не запускай побочные эффекты оборудования, сети или GUI на случайных входах без подходящего harness.
5. Выполни property tests. При сбое сохрани уменьшенный вход, точную команду, версию библиотеки и воспроизводимый regression example. Seed сам по себе не гарантирует воспроизведение на другой версии.
6. Классифицируй сбой: дефект продукта, неверное свойство/генератор или неуточненный контракт. Исправляй тест при ошибке в свойстве; сохраняй честное падение при нарушении поддержанного контракта продукта.

Новую зависимость в рабочий проект добавляй в рамках согласованной задачи и его dependency policy. Для разрешенного эксперимента достаточно временного изолированного окружения; не меняй проектный lockfile ради пилота.

## Границы

- Для обычной архитектуры автотестов используй `autotest-engineer`; для поиска новых defect families через grammar/coverage fuzzing — `fuzzing-bug-hunter`.
- Для поиска аналогов уже известного дефекта используй `variant-analysis`.
- Этот skill не выбирает поведение продукта вместо владельца требований и не превращает supported-positive кейсы в negative ради зеленого прогона.
- Не утверждай, что генерация покрыла весь домен: отчет относится к выполненным примерам и выбранным стратегиям.

В результате укажи свойство и источник контракта, домен, команду/бюджет, фактический результат и минимальный контрпример при его наличии. Разделяй проверку тестовой методики и новый баг в рабочем коде.
