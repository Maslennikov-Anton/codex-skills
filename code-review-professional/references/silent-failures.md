# Скрытые ошибки и ложный успех

Экспериментальная адаптация проверки Anthropic Silent Failure Hunter. Источник/изменения: [upstream.md](upstream.md). Это checklist текущего review, не запуск отдельного агента.

Проследи error → handler/fallback/retry → caller → наблюдаемый outcome. Начни с измененных error paths и затронутого контракта:

- Не превращается ли сбой обязательного чтения в «пустой список», отсутствие данных — в «все успешно»?
- После исчерпания retries сохраняется ли failure, причина и нужный cleanup?
- Не перехватывает ли broad catch ошибки программирования вместе с ожидаемым отказом? Доходит ли signal до ответственного caller/оператора без утечки секретов?
- Не заменяет ли fallback реальный продукт mock/stub-ом вне оговоренного режима?
- Разделены ли result продукта, полнота выполнения и публикация artifacts? Exit 0 uploader не доказывает, что все results/attachments пришли на сервер.

Сначала воспроизведи существенный error path изолированным fault injection либо докажи его кодом. Укажи конкретное потерянное условие, observable impact и строку, где возникает ложный успех. Не перечисляй гипотетические исключения без связи с изменением.

Не каждый catch/fallback — defect. Best-effort diagnostics, optional cache miss и идемпотентный cleanup могут корректно продолжать работу, если основной контракт и нужная диагностика сохранены. Не требуй UI alert на каждую внутреннюю ошибку и не переноси чужие logging/Sentry conventions. Severity определяется воздействием, а не шириной `except` сама по себе.
