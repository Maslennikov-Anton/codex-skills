# Playwright Patterns

## Сценарий проверки

Минимальный сценарий должен отвечать на один вопрос: пользовательский flow работает или нет. Не смешивай smoke, visual audit и глубокую диагностику в одном скрипте без необходимости.

Базовый порядок:

1. Открыть страницу и дождаться стабильного состояния.
2. Проверить ключевой видимый элемент.
3. Выполнить пользовательские действия.
4. Проверить observable outcome: URL, текст, role, response, state.
5. Собрать screenshot или logs, если результат нужно показать пользователю.

## Селекторы

Предпочитай:

- `getByRole` для кнопок, ссылок, полей и landmark-элементов.
- `getByLabel` для форм.
- `getByText` для стабильного пользовательского текста.
- `getByTestId` для сложных компонентов, если проект уже использует test ids.

Избегай:

- длинных CSS chains;
- nth-child без причины;
- селекторов, завязанных на декоративные классы;
- ожиданий на скрытые implementation details.

## Ожидания

Используй ожидания по условию:

- `await expect(locator).toBeVisible()`;
- `await expect(page).toHaveURL(...)`;
- `await page.waitForResponse(...)`;
- `await expect(locator).toHaveText(...)`;
- `await expect(locator).toBeEnabled()`.

`waitForTimeout` допустим только как временная диагностика, не как финальное решение.

## Diagnostics

Для багов собирай компактный набор evidence:

- текущий URL;
- screenshot;
- console errors;
- failed network requests;
- текст assertion failure;
- шаг, на котором сценарий сломался.

Для flaky-проблем добавляй trace/video только когда простой лог не объясняет причину.

## Безопасность

- Не вводи реальные пароли и токены в сценарии, если пользователь явно не дал тестовые credentials.
- Не выполняй покупки, отправку форм, массовые изменения данных и другие irreversible actions без явного подтверждения.
- На внешних сайтах ограничивайся чтением, навигацией и безопасными проверками.
